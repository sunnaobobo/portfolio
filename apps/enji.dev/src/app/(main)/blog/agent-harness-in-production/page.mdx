在许多企业核心业务里，非结构化或半结构化文档的清洗转换一直是最消耗运营人力的环节之一。以航司优惠政策投放为例，不同航司发来的文件横跨多工作表复杂 Excel、合并单元格表格与非固定排版规则，单份文件依靠人工拆解转换往往耗时近 2 小时。

当我们尝试引入大语言模型实现自动化时很快发现：**写好一段 Prompt 只能跑通 Demo，真正决定 Agent 能否上生产接管业务的，是包裹在模型外围的那套确定性工程体系——即 Agent Harness。**

---

## 为什么单次 Prompt 抽取走不通？

早期最直观的思路是“把原始表格内容塞给模型，让模型直接输出目标 JSON”。但在真实生产数据面前，这种方式很快撞上三堵墙：

1. **Token 膨胀与截断失真**：一份包含数千行航线组合与退改签附注的表格，直接序列化进上下文不仅推理缓慢，还会引发严重的中间行遗漏（Lost in the Middle）。
2. **数值与组合计算幻觉**：票面扣率换算、适用班期排除、单程组合拆解本质上是确定性逻辑运算，让概率模型直接口算极易出现细微偏差。
3. **规则长尾迭代高昂**：每接入一家新航司或遇到节假日特殊条款，全量修改主 Prompt 极易导致“改好新航司、退化老航司”。

因此，我们将范式从“模型直接生成结果数据”切换为 **“模型理解结构与业务语义，自主生成并执行 Python 转换脚本，由确定性代码产出标准文件”**。

---

## 四层 Harness 架构设计

为了驾驭“模型动态写代码并执行”带来的不确定性，我们将系统拆解为四个相互咬合的工程层。

### 1. 基于 ReAct 的统一上下文与工具闭环

依托 Spring AI Alibaba 与 MCP（Model Context Protocol）协议，我们将底层能力标准化为原子工具集：文件元信息探查（Sheet 列表、表头采样）、标准投放模板匹配、Python 脚本沙箱执行、结果格式校验以及 OSS 归档上传。

```java {title:PolicyParseAgentLoop.java}
public ParseArtifact executeTask(PolicyTask task) {
  AgentContext context = workspaceManager.initContext(task);
  for (int step = 0; step < MAX_REACT_STEPS; step++) {
    AgentAction action = llmClient.decideNextAction(context.toPromptMessages());
    if (action.isFinish()) {
      return artifactValidator.verifyAndCollect(context);
    }
    ToolObservation obs = mcpToolDispatcher.invoke(context.workspaceId(), action);
    context.recordStep(action, obs);
  }
  throw new AgentStepExceededException(task.getId());
}
```

模型不再盲目一次性写完所有逻辑：它会先采样读取前 20 行理解表头布局，编写转换脚本试运行；如果脚本报错或校验器指出某必填字段缺失，结构化错误堆栈会作为 Observation 回流至上下文，驱动模型自主定位修正。

### 2. 任务级工作区与可控执行沙箱

允许 LLM 动态生成 Python 脚本并在服务端运行，最大的隐患是**并发数据串扰**与**异常脚本影响宿主进程**。我们在执行层落地了严格隔离：

- **目录级物理隔离**：每次任务分配独立临时工作区，仅挂载当前任务的输入源文件与输出目录，执行完毕并上传 OSS 后自动销毁回收。
- **权限与依赖白名单**：限制脚本仅能导入 `pandas`、`openpyxl`、`re`、`datetime` 等数据处理白名单模块，禁用外部网络套接字与越权系统调用。
- **资源配额与超时熔断**：限制子进程内存上限与最大 CPU 执行时长，防止死循环或内存泄漏拖垮核心 Java 宿主服务。

### 3. 离线门禁与线上金标双轨评测

没有评测体系支撑的 Agent 迭代无异于盲人摸象。我们构建了离线与线上联动的双轨度量：

| 评测维度     | 离线分层质量门禁                           | 线上运营复核金标监控                   |
| ------------ | ------------------------------------------ | -------------------------------------- |
| 产物可用性   | 校验生成 Excel 结构合法、无空表与乱码      | 监控下游验价与投放接口一次通过率       |
| 行数完整性   | 对比黄金集预期航线展开条数，拦截漏行       | 追踪运营人工增删行比例                 |
| 字段级准确率 | 核心字段（舱位、票面价、旅行日期）精确比对 | 以运营最终复核发布版本作为真实金标对账 |

线上运营的角色由此从“从零手工制表”转变为“在可视化界面复核模型产物”，而每一次人工微调修正，又自然沉淀为最宝贵的真实金标数据。

### 4. 字段级航司规则自进化闭环

如何让系统越用越聪明，同时绝不破坏存量航司的稳定性？我们设计了 **“字段反馈—AI 冲突检测与候选生成—回归评测—审核发布”** 四步闭环：

1. **字段级差异拆解**：对比 Agent 原始输出与运营复核终稿，精准定位发生人工修改的具体字段及原文件上下文。
2. **冲突检测与分流**：由规则提炼模型分析差异原因——若与该航司既有规则存在语义矛盾或样本上下文缺失无法复现，自动转交人工确认；其余清晰模式自动合成为候选规则补丁。
3. **黄金集与 `pass^3` 门禁验证**：候选规则必须同时跑通该航司历史黄金集与错题集，且连续 3 次独立执行全部通过（`pass^3`）以排除随机性，彻底阻断历史能力退化。
4. **版本化灰度与回滚**：审核通过的规则按版本号快照发布，任意批次出现异常均可一键秒级回滚至上一稳定版本。

## 落地成效与工程复盘

这套架构从首版上线到持续自进化迭代后，交出了扎实的数据答卷：

- 端到端文件解析准确率从首版的 **76.4%** 稳步提升至 **92.1%**；
- 单份政策文件平均解析耗时从 **2 小时** 压缩至 **5 分钟**；
- 候选规则自动验证发布通过率达 **87%**，40 家航司的规则建设周期从 **15 天缩短至 3 天**。

回看整个过程，最深刻的体会是：**大模型负责拓宽系统能够处理的非结构化边界，而传统的软件工程功底——隔离、契约、回归测试与可观测性——决定了这个边界内的可靠性上限。**
